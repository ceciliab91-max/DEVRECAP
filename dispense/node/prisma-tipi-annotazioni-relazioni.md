### I tipi di campo
Nella dispensa precedente, Prisma e MySQL: gestione delle tabelle , abbiamo collegato MySQL a Prisma con un solo model, Product . Il punto di partenza di oggi è quello schema, invariato: generator client { provider = "prisma-client-js" } datasource db { provider = "mysql" } model Product { id Int @id @default(autoincrement()) name String price Decimal @db.Decimal(10, 2) description String? inStock Boolean @default(true) createdAt DateTime @default(now()) } Ogni tipo Prisma diventa un tipo MySQL preciso: Tipo Prisma MySQL Uso String VARCHAR(191) testo breve (nome, email) Boolean TINYINT(1) vero/falso Int INT intero a 32 bit BigInt BIGINT intero a 64 bit Float DOUBLE decimale approssimato Decimal DECIMAL(65,30) decimale esatto: prezzi DateTime DATETIME(3) data e ora Json JSON dati strutturati Bytes LONGBLOB dati binari Float vs Decimal : Float ha imprecisioni binarie ( 0.1 + 0.2 !== 0.3 ); per i valori monetari usiamo Decimal , come già fa price . Accanto a un campo puoi scrivere anche il nome di un altro model (campo di relazione, lo vediamo a partire dal capitolo 3) oppure un enum definito da te (lo vediamo nel capitolo 6). Le liste scalari come String[] non esistono su MySQL: una lista di valori si modella con una tabella di collegamento (capitoli 5 e 6). Gli attributi nativi @db.&lt;Tipo&gt; rifiniscono il mapping quando il default non basta: Attributo MySQL Quando serve @db.VarChar(255) VARCHAR(255) testo più lungo di 191 @db.Text TEXT (65 KB) descrizioni, biografie @db.LongText LONGTEXT (4 GB) testi molto lunghi @db.TinyInt / @db.SmallInt TINYINT / SMALLINT interi piccoli @db.UnsignedInt INT UNSIGNED solo positivi @db.Decimal(10, 2) DECIMAL(10, 2) precisione personalizzata @db.Date / @db.Time(3) DATE / TIME(3) solo data / solo ora Attenzione alle colonne di relazione : la FK deve avere lo stesso tipo (attributi @db.* inclusi) della colonna a cui punta. Le nostre chiavi primarie sono Int firmato, quindi le FK sono Int semplici: una @db.UnsignedInt che punta a una INT firmata viene rifiutata da MySQL con l'errore 3780. Dal vivo: da VARCHAR a TEXT Le descrizioni dei prodotti possono essere lunghe: passiamo description da VARCHAR(191) a TEXT . description String? @db.Text pnpm migrate --name description-to-text pnpm generate Verifica in Prisma Studio ( pnpm studio ): controlla che la colonna description accetti ora testo lungo.

### Le annotazioni
Quattro simboli, quattro ambiti: Simbolo Ambito Esempi @ singolo campo @id , @unique , @default(...) , @relation(...) @@ intero model @@index([...]) , @@unique([...]) , @@map("...") ? dopo il tipo colonna nullable ( description String? ) [] dopo il tipo lista, lato «molti» di una relazione @id e @default sono due cose diverse: @id definisce il ruolo del campo (chiave primaria); @default(...) definisce chi fornisce il valore se non lo passi tu. autoincrement() sta dentro @default perché è una strategia di riempimento, come now() per createdAt e true per inStock . Altre strategie: uuid() , cuid() , nanoid() (id casuali per String ), valori letterali, membri di enum. Dal vivo: tracciare le modifiche dei prodotti updatedAt DateTime @updatedAt @updatedAt non è un default: Prisma lo imposta alla creazione e lo ricalcola a ogni update . pnpm migrate --name add-updated-at pnpm generate Verifica in Prisma Studio ( pnpm studio ): modifica un prodotto e controlla che updatedAt cambi da solo.

### Relazione uno-a-uno: User e Profile
User ──────1── Profile Un utente ha al massimo un profilo. La foreign key vive nel model «dipendente» e porta @unique : è quello che rende la relazione 1:1 — senza sarebbe 1:N. model User { id Int @id @default(autoincrement()) email String @unique name String password String // Singolare e opzionale: l'utente può esistere senza profilo. profile Profile? } model Profile { id Int @id @default(autoincrement()) bio String? @db.Text avatar String? // FK con @unique: UN solo profilo per utente. userId Int @unique user User @relation(fields: [userId], references: [id]) } pnpm migrate --name add-user-profile pnpm generate Verifica in Prisma Studio ( pnpm studio ): crea un utente e un profilo, poi prova a collegare un secondo profilo allo stesso utente — viene rifiutato, perché userId è @unique . Nel database esiste una sola colonna nuova: Profile.userId INT NOT NULL UNIQUE . profile e user sono campi virtuali : non diventano colonne, esistono solo nello schema Prisma per rappresentare la relazione. password è un campo dimostrativo per mostrare una tabella «simil autenticazione»: questa lezione non implementa login o hashing. In un progetto reale la colonna conterrebbe l'hash (bcrypt/argon2) e mai la password in chiaro, e non andrebbe mai esposta all'esterno dell'applicazione. Model Colonne fisiche Campi virtuali User id PK, email UK, name , password profile Profile id PK, bio , avatar , userId FK/UK user

### Relazione uno-a-molti: Category e Product
Category ──────&lt; Product Una categoria ha molti prodotti; un prodotto appartiene a una categoria. La FK vive nel lato «molti», senza @unique : model Category { id Int @id @default(autoincrement()) name String @unique products Product[] } In Product si aggiungono la colonna fisica e il campo virtuale: model Product { // ... campi esistenti ... categoryId Int category Category @relation(fields: [categoryId], references: [id], onDelete: Cascade) @@index([categoryId]) } Attenzione ai dati esistenti : la nuova colonna obbligatoria non ha un valore valido per i prodotti già inseriti. In un database didattico si svuota la tabella prima della migration: mysql -u prisma_user -p express_store -e "DELETE FROM Product;" pnpm migrate --name add-categories pnpm generate onDelete stabilisce cosa fare ai record collegati quando il record «uno» viene eliminato: Valore Effetto Nel nostro schema Cascade elimina anche i collegati Category → prodotti; righe del ponte ProductTag quando si elimina prodotto o tag SetNull azzera la FK (richiede colonna opzionale) — Restrict rifiuta l'eliminazione default per le FK obbligatorie, es. OrderItem → Product Verifica in Prisma Studio ( pnpm studio ): crea una categoria, poi un prodotto con quella categoryId — dall'interfaccia puoi navigare dal prodotto alla sua categoria e viceversa.

### Molti-a-molti esplicita: i tag
Product &gt;──────&lt; Tag (via ProductTag) Un prodotto ha molti tag, un tag contrassegna molti prodotti. Su MySQL si modella con una tabella di collegamento scritta da noi (model ponte): due relazioni 1:N dentro lo stesso model. model Tag { id Int @id @default(autoincrement()) name String @unique products ProductTag[] } model ProductTag { id Int @id @default(autoincrement()) productId Int product Product @relation(fields: [productId], references: [id], onDelete: Cascade) tagId Int tag Tag @relation(fields: [tagId], references: [id], onDelete: Cascade) // La COPPIA è unica: lo stesso tag una volta sola per prodotto. @@unique([productId, tagId]) @@index([tagId]) } In Product si aggiunge il lato «molti»: tags ProductTag[] pnpm migrate --name add-tags pnpm generate Collegare i tag non richiede di scrivere SQL sulla tabella ponte: basta un record ProductTag con productId e tagId . Verifica in Prisma Studio ( pnpm studio ): crea a mano una riga ProductTag con productId e tagId validi.

### Molti-a-molti esplicita con dati: gli ordini
Order &gt;──────&lt; Product (via OrderItem: quantity, unitPrice) Il legame tra ordine e prodotto ha dati propri (quanti? a quale prezzo?): il model ponte li contiene. Il primo enum dello schema valida lo stato dell'ordine direttamente a livello di database. enum OrderStatus { PENDING PAID SHIPPED CANCELLED } model Order { id Int @id @default(autoincrement()) status OrderStatus @default(PENDING) createdAt DateTime @default(now()) items OrderItem[] } model OrderItem { id Int @id @default(autoincrement()) // Dati del legame: valgono per questa riga d'ordine. quantity Int @default(1) unitPrice Decimal @db.Decimal(10, 2) orderId Int order Order @relation(fields: [orderId], references: [id], onDelete: Cascade) productId Int product Product @relation(fields: [productId], references: [id]) @@index([orderId]) } In Product si aggiunge: orderItems OrderItem[] pnpm migrate --name add-orders pnpm generate unitPrice è uno snapshot : il prezzo del prodotto al momento dell'ordine . Se il prezzo del prodotto cambia, gli ordini vecchi restano com'erano. Verifica in Prisma Studio ( pnpm studio ): crea un Order e una riga OrderItem collegata, poi cambia il prezzo del prodotto e controlla che unitPrice sullo storico non cambi.

### Relazione uno-a-molti: User e Order
User ──────&lt; Order Finora gli ordini erano «anonimi»: nessun collegamento a un utente. Chiudiamo lo schema con l'ultima relazione, la stessa forma 1:N già vista per Category / Product : la FK obbligatoria vive nel lato «molti» ( Order ), senza @unique . model User { // ... campi esistenti ... orders Order[] } model Order { // ... campi esistenti ... userId Int user User @relation(fields: [userId], references: [id]) @@index([userId]) } Attenzione ai dati esistenti : come già visto per add-categories , la nuova colonna obbligatoria non ha un valore valido per gli ordini creati nei test precedenti. Si svuotano prima della migration: mysql -u prisma_user -p express_store -e "DELETE FROM OrderItem; DELETE FROM \`Order\`;" pnpm migrate --name add-user-orders pnpm generate Nessun onDelete esplicito: una FK obbligatoria ha come default Restrict — lo stesso comportamento già visto per OrderItem → Product . Un utente con ordini collegati non può essere eliminato. Verifica in Prisma Studio ( pnpm studio ): crea un utente e un ordine collegato, poi prova a eliminare l'utente — l'operazione viene rifiutata.

### Lo schema finale dello store
Con il collegamento tra User e Order lo schema raggiunge la sua forma finale: nove model in tutto. generator client { provider = "prisma-client-js" } datasource db { provider = "mysql" } model Product { id Int @id @default(autoincrement()) name String price Decimal @db.Decimal(10, 2) description String? @db.Text inStock Boolean @default(true) createdAt DateTime @default(now()) updatedAt DateTime @updatedAt categoryId Int category Category @relation(fields: [categoryId], references: [id], onDelete: Cascade) tags ProductTag[] orderItems OrderItem[] @@index([categoryId]) } model Category { id Int @id @default(autoincrement()) name String @unique products Product[] } model User { id Int @id @default(autoincrement()) email String @unique name String password String profile Profile? orders Order[] } model Profile { id Int @id @default(autoincrement()) bio String? @db.Text avatar String? userId Int @unique user User @relation(fields: [userId], references: [id]) } model Tag { id Int @id @default(autoincrement()) name String @unique products ProductTag[] } model ProductTag { id Int @id @default(autoincrement()) productId Int product Product @relation(fields: [productId], references: [id], onDelete: Cascade) tagId Int tag Tag @relation(fields: [tagId], references: [id], onDelete: Cascade) @@unique([productId, tagId]) @@index([tagId]) } enum OrderStatus { PENDING PAID SHIPPED CANCELLED } model Order { id Int @id @default(autoincrement()) status OrderStatus @default(PENDING) createdAt DateTime @default(now()) items OrderItem[] userId Int user User @relation(fields: [userId], references: [id]) @@index([userId]) } model OrderItem { id Int @id @default(autoincrement()) quantity Int @default(1) unitPrice Decimal @db.Decimal(10, 2) orderId Int order Order @relation(fields: [orderId], references: [id], onDelete: Cascade) productId Int product Product @relation(fields: [productId], references: [id]) @@index([orderId]) } Le cinque relazioni costruite, in sintesi: Category ──────&lt; Product &gt;──────&lt; Tag (via ProductTag) Product &gt;──────&lt; Order (via OrderItem: quantity, unitPrice) User ──────1── Profile User ──────&lt; Order Relazione Model FK fisica Dove sta 1:1 User ↔ Profile Profile.userId UNIQUE lato dipendente 1:N Category ↔ Product Product.categoryId (+ indice) lato «molti» M:N esplicita Product ↔ Tag ProductTag.productId + ProductTag.tagId model ponte M:N esplicita Order ↔ Product OrderItem.orderId + OrderItem.productId model ponte con dati 1:N User ↔ Order Order.userId (+ indice) lato «molti» Verifica finale in Prisma Studio ( pnpm studio ): nove tabelle, l'enum nella colonna status di Order , e le foreign key con i rispettivi indici. Nella prossima dispensa lo mettiamo alla prova e ci costruiamo sopra l'API REST completa dello store con Express.

```javascript
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "mysql"
}

model Product {
  id          Int      @id @default(autoincrement())
  name        String
  price       Decimal  @db.Decimal(10, 2)
  description String?
  inStock     Boolean  @default(true)
  createdAt   DateTime @default(now())
}
```

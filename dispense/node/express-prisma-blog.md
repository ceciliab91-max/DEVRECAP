### Progettare lo schema su DrawSQL
Prima si disegna, poi si scrive codice: su drawsql.app progettiamo tabelle e relazioni in modo visuale, senza ancora pensare alla sintassi di Prisma. Il blog ha post e tag . Un post può avere più tag e lo stesso tag può stare su più post: è una relazione molti-a-molti (N:N). In un database relazionale non si collega direttamente Post a Tag : serve una terza tabella, detta tabella ponte , in cui ogni riga dice «questo post ha questo tag». Tabella Colonne A cosa serve Post id , title , content Gli articoli del blog Tag id , name Le etichette (es. «prisma», «express») PostTag id , post_id , tag_id Il ponte: una riga per ogni coppia post–tag Su DrawSQL le relazioni si disegnano trascinando la colonna chiave esterna sulla chiave primaria a cui punta: PostTag.post_id → Post.id e PostTag.tag_id → Tag.id . Entrambe sono molti-a-uno viste dal ponte: tante righe di PostTag puntano allo stesso post (o allo stesso tag). Lo schema del blog disegnato su DrawSQL. Esercizio Il post «Introduzione a Prisma» ha i tag «prisma» e «database». Il post «Rotte in Express» ha i tag «express» e «prisma». Quante righe ci sono in PostTag ? E quante in Tag ? Mostra soluzione Tag: 3 righe → prisma, database, express («prisma» è UNO solo, condiviso) PostTag: 4 righe → (post 1, prisma) (post 1, database) (post 2, express) (post 2, prisma)

### Controllare lo schema prima della migrazione
L'AI scrive in fretta ma sbaglia con sicurezza: lo schema generato si legge riga per riga prima di lanciare pnpm migrate , perché la migrazione modifica il database vero. Un risultato corretto somiglia a questo. Le righe generator e datasource restano quelle sistemate nel capitolo 1 : all'AI chiediamo solo i model. model Post { id Int @id @default(autoincrement()) title String @db.VarChar(255) content String @db.Text tags PostTag[] } model Tag { id Int @id @default(autoincrement()) name String @db.VarChar(50) posts PostTag[] } model PostTag { id Int @id @default(autoincrement()) postId Int @map("post_id") post Post @relation(fields: [postId], references: [id], onDelete: Cascade) tagId Int @map("tag_id") tag Tag @relation(fields: [tagId], references: [id], onDelete: Cascade) // La COPPIA è unica: lo stesso tag una volta sola per post. @@unique([postId, tagId]) } La checklist Controlla che... Perché generator e datasource siano quelli del progetto L'AI a volte aggiunge url = env(...) nel datasource: con Prisma 7 la connessione sta in prisma.config.ts Ogni @relation abbia il campo inverso PostTag.post richiede Post.tags , altrimenti Prisma dà errore di validazione Le chiavi esterne siano Int come gli id Tipi diversi fanno fallire la relazione content sia @db.Text Un String semplice in MySQL diventa VARCHAR(191) : troppo corto per un articolo Ci sia @@unique([postId, tagId]) Senza, lo stesso tag può finire due volte sullo stesso post Ci sia onDelete: Cascade sul ponte Senza, eliminare un post che ha dei tag fallisce Solo quando la checklist è tutta verde: pnpm validate # controlla che lo schema sia valido pnpm migrate --name blog # crea la migration e la applica al database pnpm generate # rigenera il client con i nuovi model Esercizio Questo model è stato generato dall'AI. ### Un post con due tag in una sola chiamata
Con le scritture annidate Prisma crea il post, i tag e le righe del ponte in una sola chiamata: niente INSERT separati e niente id da passare a mano. Cosa fa create Inserisce una nuova riga nella tabella del model. I valori delle colonne vanno in data ; l' id non si passa, lo genera il database con autoincrement() . // SQL: INSERT INTO Post (title, content) VALUES ('Ciao', 'Primo post'); await client.post.create({ data: { title: "Ciao", content: "Primo post" } }); Opzione A cosa serve data I valori della nuova riga. Può contenere anche le relazioni ( create , connect ): è la scrittura annidata di questo capitolo select / include Quali campi e relazioni restituire nella risposta (facoltativo) Restituisce : la riga appena creata, id compreso. Se viola un vincolo (per esempio un @unique ) lancia un errore. La scrittura annidata Per un post con due tag, in SQL servirebbero cinque INSERT (un post, due tag, due righe di PostTag ) e dovremmo recuperare ogni id generato per usarlo nella query successiva. Con Prisma descriviamo invece la forma dei dati, seguendo le relazioni dello schema: Post → tags (PostTag) → tag (Tag) . Crea un file seed.js nella radice del progetto: import "dotenv/config"; import { client } from "./prisma-client.js"; const post = await client.post.create({ data: { title: "Introduzione a Prisma", content: "Prisma è un ORM per Node.js...", // tags è la lista di righe PostTag collegate al post. tags: { // Crea DUE righe nel ponte... create: [ // ...e per ognuna crea anche il Tag a cui punta. { tag: { create: { name: "prisma" } } }, { tag: { create: { name: "database" } } } ] } }, // Nella risposta vogliamo anche le righe del ponte, con il tag dentro. include: { tags: { include: { tag: true } } } }); console.log(JSON.stringify(post, null, 2)); await client.$disconnect(); node seed.js Il risultato mostra la struttura a tre livelli. postId e tagId li ha compilati Prisma da solo: { "id": 1, "title": "Introduzione a Prisma", "content": "Prisma è un ORM per Node.js...", "tags": [ { "id": 1, "postId": 1, "tagId": 1, "tag": { "id": 1, "name": "prisma" } }, { "id": 2, "postId": 1, "tagId": 2, "tag": { "id": 2, "name": "database" } } ] } Collegare un tag che esiste già Al posto di create si usa connect , indicando l' id del tag esistente. È quello che faremo nella rotta POST. await client.post.create({ data: { title: "Rotte in Express", content: "Un router raggruppa le rotte...", tags: { create: [ { tag: { connect: { id: 1 } } }, // "prisma", esiste già { tag: { create: { name: "express" } } } // nuovo ] } } }); Esercizio Crea il post «Relazioni N:N» collegato ai tag già esistenti con id 1 e 2. Mostra soluzione await client.post.create({ data: { title: "Relazioni N:N", content: "Una tabella ponte collega due tabelle...", tags: { create: [ { tag: { connect: { id: 1 } } }, { tag: { connect: { id: 2 } } } ] } } });

### Prisma dentro Express
server.js avvia l'app e monta i router; le rotte dei post stanno in routers/postRouter.js , che importa il client Prisma creato una volta sola in prisma-client.js . Installiamo Express nello stesso progetto. La struttura è quella vista nella dispensa sul Router di Express : pnpm add express hello-blog/ ├── prisma/ │ └── schema.prisma ├── routers/ │ └── postRouter.js ├── prisma-client.js └── server.js server.js import express from "express"; import postRouter from "./routers/postRouter.js"; const app = express(); // Senza questa riga req.body è undefined nelle rotte POST e PUT. app.use(express.json()); // Tutte le rotte di postRouter iniziano con /blogs. app.use("/blogs", postRouter); app.listen(3000, () => { console.log("Server in ascolto su http://localhost:3000"); }); routers/postRouter.js import express from "express"; import { client } from "../prisma-client.js"; const router = express.Router(); // ...qui le rotte dei prossimi capitoli... export default router; Dato che il router è montato su /blogs , al suo interno i percorsi sono relativi: router.get("/") risponde a GET /blogs e router.get("/:id") a GET /blogs/:id . Ogni query Prisma restituisce una Promise, quindi i gestori delle rotte sono async e usano await . Il try/catch intercetta gli errori del database e risponde con un errore invece di far cadere il server.

### GET /blogs: la lista dei post
findMany legge più righe; con select annidato scegliamo esattamente quali campi tornano, anche dentro le relazioni. Cosa fa findMany Legge tutte le righe che rispettano un filtro. Senza opzioni restituisce l'intera tabella. // SQL: SELECT * FROM Post; await client.post.findMany(); // SQL: SELECT id, title FROM Post WHERE title LIKE '%Prisma%' ORDER BY id DESC; await client.post.findMany({ where: { title: { contains: "Prisma" } }, select: { id: true, title: true }, orderBy: { id: "desc" } }); Opzione A cosa serve where Quali righe: il filtro, come il WHERE di SQL select Solo i campi elencati, anche dentro le relazioni include Tutti i campi, più le relazioni indicate orderBy L'ordine: "asc" o "desc" take / skip Quante righe prendere / quante saltarne Restituisce : un array , vuoto ( [] ) se nessuna riga corrisponde. Non lancia mai un errore per «non trovato». Con include otterremmo tutte le colonne del ponte ( id , postId , tagId ), che al client non servono. Con select chiediamo solo quello che vogliamo mostrare: router.get("/", async (req, res) => { try { const posts = await client.post.findMany({ select: { id: true, title: true, // Attraverso il ponte prendiamo solo il nome del tag. tags: { select: { tag: { select: { id: true, name: true } } } } }, orderBy: { id: "desc" } }); res.json(posts); } catch (error) { res.status(500).json({ error: "Errore del server" }); } }); [ { "id": 1, "title": "Introduzione a Prisma", "tags": [ { "tag": { "id": 1, "name": "prisma" } }, { "tag": { "id": 2, "name": "database" } } ] } ] Appiattire i tag Quel { "tag": { ... } } è la riga del ponte: al frontend basta la lista dei tag. Una piccola funzione, in cima a postRouter.js , la «appiattisce» con map : // Da [{ tag: { id, name } }] a [{ id, name }]. const flattenTags = (post) => ({ ...post, tags: post.tags.map((postTag) => postTag.tag) }); // Nella rotta: res.json(posts.map(flattenTags)); Esercizio Modifica GET /blogs per restituire anche i primi 100 caratteri di content in un campo excerpt . Mostra soluzione const posts = await client.post.findMany({ select: { id: true, title: true, content: true, tags: { select: { tag: { select: { id: true, name: true } } } } } }); res.json(posts.map((post) => { const { content, ...rest } = flattenTags(post); return { ...rest, excerpt: content.slice(0, 100) }; }));

### GET /blogs/:id: un solo post
findUnique cerca per id e restituisce null se non trova nulla: in quel caso rispondiamo 404 . Cosa fa findUnique Legge una sola riga , cercandola per un campo che la identifica in modo univoco: l' @id o un campo @unique . Per filtrare su altri campi si usa findFirst . // SQL: SELECT * FROM Post WHERE id = 1; await client.post.findUnique({ where: { id: 1 } }); Opzione A cosa serve where Obbligatorio: il campo univoco da cercare (qui id ) select / include Quali campi e relazioni restituire, come in findMany Restituisce : un oggetto , oppure null se la riga non esiste. Per questo controlliamo if (!post) . I parametri dell'URL arrivano sempre come stringhe: req.params.id vale "1" , non 1 . Prisma vuole un Int , quindi lo convertiamo con Number() . router.get("/:id", async (req, res) => { const id = Number(req.params.id); try { const post = await client.post.findUnique({ where: { id }, select: { id: true, title: true, content: true, tags: { select: { tag: { select: { id: true, name: true } } } } } }); if (!post) { return res.status(404).json({ error: "Post non trovato" }); } res.json(flattenTags(post)); } catch (error) { res.status(500).json({ error: "Errore del server" }); } }); Esercizio Cosa succede con GET /blogs/abc ? Aggiungi un controllo che risponda 400 se l'id non è un numero. Mostra soluzione // Number("abc") è NaN: Prisma lancerebbe un errore di validazione (500). const id = Number(req.params.id); if (Number.isNaN(id)) { return res.status(400).json({ error: "Id non valido" }); }

### POST /blogs: creare un post
I dati arrivano in req.body (grazie a express.json() ). La query è la scrittura annidata del capitolo 5, con connect per collegare tag esistenti. È la stessa create vista nel capitolo 5 : cambia solo la provenienza dei dati, che ora arrivano dal client invece di essere scritti nel codice. Il client manda titolo, contenuto e la lista degli id dei tag: { "title": "Rotte in Express", "content": "Un router...", "tagIds": [1, 3] } Con map trasformiamo ogni id nella riga del ponte da creare: router.post("/", async (req, res) => { const { title, content, tagIds = [] } = req.body; if (!title || !content) { return res.status(400).json({ error: "title e content sono obbligatori" }); } try { const post = await client.post.create({ data: { title, content, // [1, 3] → [{ tag: { connect: { id: 1 } } }, { tag: { connect: { id: 3 } } }] tags: { create: tagIds.map((id) => ({ tag: { connect: { id } } })) } }, select: { id: true, title: true, content: true, tags: { select: { tag: { select: { id: true, name: true } } } } } }); // 201 Created: è stata creata una nuova risorsa. res.status(201).json(flattenTags(post)); } catch (error) { res.status(500).json({ error: "Errore del server" }); } }); curl -X POST -H "Content-Type: application/json" \ -d '{"title":"Rotte in Express","content":"Un router...","tagIds":[1,3]}' \ http://localhost:3000/blogs Il select è lo stesso in tre rotte: puoi salvarlo in una costante ( const postSelect = { ... } ) e riusarlo.

### PUT /blogs/:id: modificare un post
update vuole un where su un campo univoco e i nuovi valori in data . Se l'id non esiste Prisma lancia l'errore P2025 . Cosa fa update Modifica una riga esistente , individuata con un campo univoco. Si scrivono solo i campi da cambiare: gli altri restano come sono. // SQL: UPDATE Post SET title = 'Nuovo titolo' WHERE id = 1; await client.post.update({ where: { id: 1 }, data: { title: "Nuovo titolo" } }); Opzione A cosa serve where Obbligatorio: quale riga, tramite @id o @unique data I nuovi valori. I campi undefined vengono ignorati select / include Quali campi e relazioni restituire (facoltativo) Restituisce : la riga dopo la modifica. Se la riga non esiste lancia l'errore P2025 . Aggiorniamo titolo e contenuto. Invece di cercare prima il post, lasciamo fare a Prisma e trasformiamo l'errore P2025 («record non trovato») in un 404: router.put("/:id", async (req, res) => { const id = Number(req.params.id); const { title, content } = req.body; try { const post = await client.post.update({ where: { id }, data: { title, content } }); res.json(post); } catch (error) { if (error.code === "P2025") { return res.status(404).json({ error: "Post non trovato" }); } res.status(500).json({ error: "Errore del server" }); } }); Se un campo non viene inviato vale undefined , e Prisma lo ignora: quel campo resta com'era. Esercizio Fai in modo che PUT accetti anche tagIds e sostituisca i tag del post. Suggerimento: dentro tags puoi usare prima deleteMany: {} e poi create . Mostra soluzione const { title, content, tagIds = [] } = req.body; await client.post.update({ where: { id }, data: { title, content, tags: { deleteMany: {}, // 1. cancella tutte le righe del ponte di questo post create: tagIds.map((tagId) => ({ tag: { connect: { id: tagId } } })) // 2. ricrea } } });

### DELETE /blogs/:id: eliminare un post
delete elimina una riga; grazie a onDelete: Cascade nello schema spariscono anche le righe di PostTag , mentre i tag restano. Cosa fa delete Elimina una riga , individuata con un campo univoco. Le righe collegate si comportano come dice onDelete nello schema. // SQL: DELETE FROM Post WHERE id = 1; await client.post.delete({ where: { id: 1 } }); Opzione A cosa serve where Obbligatorio: quale riga, tramite @id o @unique Restituisce : la riga appena eliminata (utile per mostrare cosa è stato cancellato). Se non esiste lancia l'errore P2025 . router.delete("/:id", async (req, res) => { const id = Number(req.params.id); try { await client.post.delete({ where: { id } }); // 204 No Content: operazione riuscita, nessun corpo nella risposta. res.sendStatus(204); } catch (error) { if (error.code === "P2025") { return res.status(404).json({ error: "Post non trovato" }); } res.status(500).json({ error: "Errore del server" }); } }); Riepilogo Le rotte sono tutte in routers/postRouter.js ; il prefisso /blogs lo aggiunge app.use in server.js .
